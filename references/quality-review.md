# 质量评审：围绕任务与证据

用于实施后的自查、用户请求的 UI 评审或多页面交付。小变更用现有检查记录即可；无需为每一个按钮生成 JSON 报告。

## 两轮评审

**第一轮检查是否做对了事**：用户主任务能否完成，约束是否保留，行为是否真实，是否改动了不相关范围。

**第二轮检查是否做得精致**：层级、密度、对齐、状态反馈、焦点、响应式和性能。构建通过不能代替这轮观察；反过来漂亮截图也不能证明操作成功。

## 五个判断维度

| 维度 | 通过时可观察到 | 需要修复的例子 |
| --- | --- | --- |
| 任务与信息 | 不读说明也能找到主要操作和关键内容 | 主按钮被装饰区挤到屏外 |
| 视觉一致性 | 字体、间距、容器与颜色有稳定关系 | 同页三套圆角、hover 和阴影体系 |
| 交互连续性 | 展开、切换、保存后能继续原任务 | 保存后草稿消失但请求失败 |
| 可访问与响应式 | 键盘、触摸、窄屏、放大与 reduced motion 可用 | hover 才有删除入口，焦点进入隐藏层 |
| 实现与性能 | 实际代码与验证支持交付结论 | 全站加载 PDF 引擎、假进度、未接线按钮 |

不计算“审美总分”。用 `通过 / 需修复 / 未验证 / 不适用` 描述每项，并写一句实际观察。问题优先级由影响决定，不由发现顺序决定。

## 证据粒度

- 编译 / 类型问题：真实执行的命令结果与对应版本环境。
- 交互问题：明确的前置状态、操作、预期与观察。
- 视觉问题：页面、视口、主题、内容状态和截图；必要时前后比较。
- 性能问题：真实测量或可复现现象，不从库名猜包体积与帧率。
- 来源问题：目标组件的当前官方 URL / revision 与选型原因。

截图命名可包含页面、视口和状态，例如 `review-mobile-error.png`，不需要复杂命名协议。测试日志和截图放在已有任务输出目录，不污染源代码目录。

## 完成边界

影响主流程、数据、关键可访问操作的缺陷应在授权范围内修复后复验。用户只要评审时，交付问题与具体建议，不擅自改代码。

工具不可用时，记录哪一项未验证及剩余风险。可以交付已完成部分，但不能把浏览器不可用改写成“视觉通过”。检查记录完整也不能被称作产品验收完成。

跨多页面时可使用 [验收模板](../templates/delivery-evidence.json) 和 `check_delivery.py`。脚本仅检查 requirement 覆盖、状态以及证据文件存在性；它不理解截图、不判断日志真假，也不会执行测试。

## 常见偏差

| 偏差 | 修正 |
| --- | --- |
| 增加组件数、文件数或测试数当作质量提升 | 回到用户任务和实际效果 |
| 只验证默认态 | 补充本次相关的失败、空值、长内容与移动状态 |
| 把下载 / 安装记录当作使用证明 | 检查业务调用与实际行为 |
| 把所有反馈都变成 Toast | 将持久错误和字段错误放回具体位置 |
| 不断调整配色而不解决信息层级 | 先改结构、内容顺序和尺度 |
| 固定要求每个小任务先提交完整方案并等待批准 | 按用户已有授权继续，只有真正缺失的决定才询问 |

## 真实任务评估

[人工场景评估](../evals/manual-scenarios.md)给出面向 Agent 的真实任务。它与离线检索测试用途不同：前者评价实现和设计行为，后者只验证脚本筛选规则。未跑过的场景必须保留为待评估，不能从脚本测试推断 Agent 效果提升。
