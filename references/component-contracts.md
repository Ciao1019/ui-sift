# 组件选择与集成契约

用于新增依赖、迁移 copy-paste 组件或组合多个来源。复杂度越高，越值得把结论记在已有设计简报里；普通本地复用只需要快速检查。

## 先判断能否采用

| 约束 | 需要的证据 | 不满足时 |
| --- | --- | --- |
| 框架与运行环境 | 官方支持、package peer dependencies、目标源码 | 不复制不兼容代码；换同栈候选或只借鉴设计 |
| 版本与基础库 | 当前 package、Tailwind、Radix / Base UI / Aria | 使用匹配变体；迁移超出任务时另选方案 |
| 业务能力 | 实际 API、状态、事件、数据模型 | 不以外观相似替代缺失行为 |
| 授权与获取 | 目标组件 / 模板许可、已有访问权限 | 不复制未授权源码，使用公共替代或说明限制 |
| 项目范围 | 本地同类组件、调用点、允许新增的依赖 | 优先复用；不擅自替换全站系统 |

脚本只做已知框架过滤与候选检索，不自动证明上表通过。

## 再比较哪一个更合适

每个真正入选的候选可用六句话比较：

```text
任务匹配：解决哪一个具体操作或信息问题？
现有覆盖：项目已有能力缺了什么？
交互价值：它在哪个状态或转换上做得更好？
视觉适配：如何映射 tokens、密度、图标和主题？
集成代价：新增包、全局样式、SSR、运行时和维护负担是什么？
结论：采用 / 仅参考 / 不选，以及原因。
```

不要把这些问题变成伪精确的 97 分排行榜。候选分数无法证明可访问性、审美或性能。

## 状态与事件先于 JSX

为非平凡组件明确：输入是什么、用户可做什么、向外触发什么、异步结果如何返回、取消是否真正停止工作、出错保留什么状态。

上传组件的状态至少区分待选、已选、上传中、成功、失败、取消；失败重试应针对正确文件。权限弹层的临时选择与已保存权限要有边界。工具结果的审批动作需要防重复执行与结果回执。

列表排序、日期范围和编辑器选区都可能有受控 / 非受控模式。选择一种与项目状态归属一致的方式，不让演示内部状态与外部数据各自维护一份事实。

## 复制源码后的接线

1. 取得组件与必要 hooks、类型、样式、资源、许可信息；记录可回溯的 URL / revision。
2. 将工具函数、aliases、图标和基础组件映射到项目已有入口。
3. 删除演示面板、虚构数据、模拟网络与无关主题切换；仅在用户明确要原型时保留标明的演示逻辑。
4. 接入真实 API / 事件，完成 loading、empty、error、disabled 与恢复流程。
5. 检查 theme Provider、reset、portal、z-index、客户端 API、SSR / hydration 和可访问语义。
6. 查看 diff，再运行项目已有检查及实际页面操作。

下载成功只说明拿到了文件；安装成功只说明依赖或源码落盘；两者都不等于行为接线和验收完成。

## 多库组合的明确归属

| 共享能力 | 应有的归属 |
| --- | --- |
| tokens / 字体 / 主题切换 | 现有应用主题为主，外来组件做适配 |
| Tooltip / Dialog / Popover | 优先同一基础体系，统一 focus 与层级行为 |
| 图标 | 一套主要图标入口，外来示例图标映射过去 |
| 动效 | 现有 CSS / Motion 能满足时不增加平行运行时 |
| Markdown 与消息状态 | 按现有消息或内容管线扩展，避免重复解析同一内容 |
| 日期与时区 | 与业务时间模型和现有日期库一致 |
| 编辑器文档值 | 编辑器 / 业务存储约定负责，展示层不私自另存数据 |

必要时可以并存不同技术，但要解释边界与代价。不能为了“一个库”强行重写正常工作的专项能力，也不能因为所有库都能安装就随意混搭。

## 来源更新时

先定位本地改动与上游新版本差异，再更新相关文件。对于 copy-paste 组件，本地业务接线可能已偏离演示源码，不能直接运行覆盖命令。当前版本文档与包依赖比历史目录条目更有权威。
