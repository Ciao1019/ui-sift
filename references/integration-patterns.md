# 通用组件集成模式

以下是按任务组织的设计模式与取舍示例，不是某个产品的代码案例，也不是已经在所有框架中验证的固定组合。实际采用哪个来源，取决于使用者自己的工程、许可与能力缺口。

## 1. 将专项能力嵌入已有界面

**适用**：已有应用只缺文档预览、导图、代码高亮等能力。

先让应用自己的外壳、导航、主题与数据状态保持连续，再在局部接入专项能力。重型内容按进入视图或用户操作加载；保留统一的加载、失败和重试行为。

例如文档导航可以使用已有树组件，预览能力再评估 Extend；导航不需要为了预览引擎而更换。导图在专门视图中加载，普通阅读不承担引擎启动成本。

**关键契约**：当前对象 id、加载状态、选择事件、错误恢复，以及切换对象时应保留的页面 / 缩放 / 草稿。

## 2. 扩展 AI 消息的内容层

**适用**：已有聊天 runtime，希望工具结果更易理解。

保留消息生命周期和数据归属；将工具返回值转换成明确类型，再按内容选择引用、表格、进度或操作卡片。可以评估 Tool UI；文本渲染沿用已有管线，需要新增时再比较 Lobe UI、assistant-ui Elements 或轻量实现。

**关键契约**：流式更新不能不断重置阅读位置；用户操作需要回执；取消与重试对应真实任务；未知进度不显示编造的百分比。只读内容不需要富文本编辑引擎。

## 3. 将 copy-paste 组件变成本地组件

**适用**：官网效果合适，但使用不同的 aliases、图标和主题。

在引入前列出组件依赖及必要文件。落地后把颜色、圆角、焦点、图标和基础控件映射到现有入口，再用真实 props、事件与状态替换演示逻辑。保留来源和必要署名。

**关键契约**：业务行为与动画展示分开；受控值由调用方负责；组件不私自维护另一份业务事实。上游更新时查看差异，避免覆盖本地接线。

## 4. 接入主题系统前检查全局影响

**适用**：引入的组件需要 Provider、reset 或独立 token 系统。

局部 JSX 包裹不代表样式隔离。检查全局选择器、根节点属性、字体 reset、portal、z-index、CSS layer 与加载顺序。让应用的主题状态保持单一来源，外来组件映射其语义颜色。

若只需要一个静态标签或简单外观，先比较现有原语与 CSS 的实现成本。若需要复杂键盘、表格或输入行为，再评估完整库带来的收益。

**验证**：组件内部、相邻内容和弹层都观察；支持明暗模式时检查切换；不能只在独立 demo 中确认颜色正常。

## 5. 从日期字段升级到日程管理

**适用**：需求包含“日历”，但操作复杂度尚未区分。

日期或日期范围字段优先沿用本地日期选择器；日 / 周视图、多事件编辑或资源排程再评估 DayFlow 等专项引擎。组件外观相近不意味着状态模型相同。

**关键契约**：单日、日期范围与带时区事件分别建模；禁用日期和业务校验一致；拖拽失败有恢复；Pro 能力需按目标功能核实。

## 6. registry 是入口，不是采用证明

某个来源出现在配置里，只说明它是可发现入口；不证明组件已安装、业务已调用或地址仍然有效。采用前核对目标组件、版本和基础库变体。

例如 Extend 官方文档区分按 style 的 registry 与旧入口，选择时应以现有 Radix / Base UI 体系为依据。不要把网上任意示例的配置整份复制进应用。

## 使用其他技术栈时

本目录的来源以 React 为主，也包含 Vue / Nuxt、Go templ 与多框架日历。框架不匹配时继续使用目标工程已有组件，或只借鉴布局和交互模式；没有对应候选不构成迁移框架的理由。

新项目依据产品需要选择基座；已有项目依据实际依赖选择接入方式。路由、请求层、图标、构建工具、目录结构和部署方式均由使用者的工程决定。
