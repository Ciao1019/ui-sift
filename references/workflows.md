# 从需求到界面的工作流

本文件说明怎样组织一次前端任务。流程产物可以是简短工作笔记、已有设计文档或代码注释；只有页面重构、多页面或跨轮次任务才值得单独保存设计简报、候选表与验收记录。流程推进以完成对应工作为依据，不自动添加人工审批节点。

## 按工作规模选择路径

| 情况 | 执行路径 | 应有的可观察结果 |
| --- | --- | --- |
| 一个控件、一个状态或局部间距 | 检查原实现 → 提出局部判断 → 修改 → 定向验证 | 改动和实际状态符合需求，无须创建全套记录 |
| 新页面或现有页面明显重构 | 任务简报 → 视觉方向 → 组件选型 → 主流程 → 细节打磨 → 验证 | 页面具备真实内容、完整状态、清晰层级 |
| 多页面或跨库工作台 | 前述路径 + 共享 tokens / 组件边界 + 页面间状态连续性 | 一套共享设计语言，导航与数据流能连起来 |
| 参考图 / 网站还原 | 拆解参考 → 对齐现有约束 → 实现关键结构 → 同视口比较 → 修正差异 | 有证据解释哪些被还原、哪些因产品要求调整 |
| UI 评审 | 观察主流程 → 按影响记录问题 → 获授权时实施修复 → 复查 | 指向实际页面和状态的可操作发现，避免泛泛打分 |

不要把没有后端的原型伪装成业务完成；明确原型范围即可。修改规则、购买服务、部署或发消息仍按任务授权处理，流程本身不授予这些权限。

## A. 任务简报：让设计判断有对象

提取用户、主任务、主要内容、关键动作、约束与成功条件。已有代码或上下文能回答的内容直接记录，不逐条盘问用户。

例如“文档工作台”仍然不够具体：

```text
用户：审核抽取结果的运营人员
主任务：发现一个错误字段，在原文定位并修正
主要内容：PDF 页与字段列表
关键动作：定位、修改、保存、下一条
约束：桌面双栏；窄屏可切视图；保留原 API；复用现有 Radix
成功条件：改字段不丢当前页，错误有恢复方式，保存状态明确
```

如果只说“更高级”，先从页面实际任务推断问题：层级平、信息太散、操作不连续、反馈缺失、颜色混乱。把审美诉求翻译为这些可以观察的变化，再决定组件。

需要持久记录时使用 [设计简报模板](../templates/design-brief.md)，不创建一份只重复用户原话的计划。

## B. 项目画像：判断哪些东西应该保留

使用 [工具手册](tooling.md) 的只读扫描器或手工检查同类证据：

- 目标 package 的框架与版本，不能只看 monorepo 根目录。
- 已有基座：Radix / Base UI / React Aria、Tailwind、主题、图标、弹层与 Toast。
- 本地组件的调用点与行为，不能仅凭文件名判断功能齐全。
- 路由、URL 状态、异步数据、权限和响应式约束。
- 哪些文件属于用户未完成的改动，避免覆盖。

得到一组明确约束，例如“React 19 + Tailwind 4 + Radix；保留当前 Markdown runtime；只新增文档预览能力”。这个约束应同时影响选型、样式与测试。

## C. 视觉方向：先确定结构，再看素材

按 [视觉语言](visual-language.md) 判断页面的内容密度、阅读方式和操作频率。只在方向确实不明确时比较两个候选；每个方向描述一项结构差异和一项代价，不只是换颜色。

```text
方向 A：列表居中，详情按需展开。浏览快、页面安静，跨项比较较慢。
方向 B：左列表右详情。适合频繁审核，占用宽度，窄屏需分层导航。
本次选 B：用户连续审核，比单纯浏览更频繁。
```

已有用户参考时，拆解其信息结构、字号关系、密度、材质、动效和导航，不擅自改成自己的默认风格。不能因为某种配色流行就把不相关页面做成同一个模板。

## D. 组件选型：先剔除不合适的，再比较优秀的

用 [组件契约](component-contracts.md) 的约束过滤：框架、版本、基础组件体系、许可、业务能力、维护成本。通过后才比较视觉和交互。

离线检索器只产出候选，不替 Agent 作最终选择。每个入选项要能说明：用来解决什么、为什么胜过现有实现、需要哪些调整。没有候选也可以用现有原语实现，不必强行从目录里挑一个。

有官方 skill / MCP 时按 [接入指南](acquisition.md) 获取对应知识。只读取所需部分；没有时下载目标源码和必要依赖，继续接线。为跨来源组合指定唯一的 tokens、图标、弹层和消息状态归属。

## E. 实现：先让主流程完成一次

顺序通常是语义结构与内容 → 数据与行为 → 全部必要状态 → 响应式 → 视觉细节 → 动效。

先完成一次真正的“选择 → 操作 → 反馈 → 继续”，再做弹性参数和高光。不要一口气复制很多漂亮组件后才发现它们使用不同的基础库和状态模型。

对于跨页面工作，先把共享组件在一个代表页面验证，随后迁移其他页面。只复用已经稳定的行为和 tokens，不把业务差异塞进过度抽象的巨型组件。

## F. 视觉与交互打磨

选择有代表性的真实内容：最长标题、空列表、加载中、一个失败项、正常成功状态。完成桌面和窄屏观察；页面支持主题切换时看两个主题。

用 [交互配方](interaction-recipes.md) 检查节奏，用 [布局与内容](layout-content.md) 处理溢出和密度。关键视图以截图比较，但焦点、滚动、取消和持续更新必须实际操作。

每次修正针对一类已观察问题，例如“标题过大导致操作区退出首屏”或“切换字段后预览跳回第一页”。不为了追求抽象高分无限改风格。

## G. 验收与跨轮次继续

按 [质量评审](quality-review.md) 核验任务结果。未完成项区分代码缺陷、环境限制和用户尚未决定的产品问题；不要把三者都叫“完成”。

如果用户修改方向，保留仍适用的组件、数据接线与测试，更新受影响的设计判断。记录只需能恢复：当前目标、已选方案、哪些文件有改动、哪些验证通过、下一步是什么。无需复制整个对话或生成内部审批账本。
